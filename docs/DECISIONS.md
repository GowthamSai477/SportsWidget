# Technical Decision Record

Status: living document. Last reviewed: 2026-08-22.
Scope decisions here are binding until a dated addendum supersedes them.

## Context

Universal sports schedule platform ("Widgets"): multi-sport schedules, results,
standings, countdowns, notifications, and — the differentiator — premium home-screen
widgets. Development mode (`DEVELOPMENT_MODE=true`) grants every entitlement; no
payments/enforcement until the core product is stable (spec §80). Phase-1 sport is
Formula 1; architecture must make sport #20 as cheap as sport #2 (§83).

## Decisions

### D1 — Mobile stack

**Expo (SDK from `create-expo-app`, currently SDK 54 line) + React Native + TypeScript**, with Expo Router (file-based navigation), TanStack Query (server state), Zustand (client/UI state only), NativeWind (Tailwind-flavored styling), FlashList (virtualized lists), expo-image.

Rationale: matches spec §17 verbatim; Expo dev builds (not Expo Go) are the target because widgets require native modules (§66). Primary device: Samsung Galaxy S25 FE (Android 15).

Consequence: `apps/mobile/android` & `ios` are generated by `expo prebuild` and gitignored; all native customization lives in versioned config plugins under `apps/mobile/plugins/`.

### D2 — Backend stack

**NestJS 11 modular monolith** (single deployable, feature modules per §71), Prisma ORM, Zod at the provider boundary, class-validator DTOs at the HTTP boundary, Swagger/OpenAPI on `/api/docs`. Rationale: §8, §44, §70 (no premature microservices). Module boundaries are kept clean enough to extract services later without rewrites.

### D3 — Database

**PostgreSQL 16** as sole source of truth, accessed only through Prisma migrations. Normalized core entities per §9; sport-specific extras in controlled JSONB metadata columns (§10) — never for frequently-filtered fields. Timestamps stored UTC (`timestamptz`), converted client-side (§48).

Deliberate deviations from §9's table list (documented, not blind):
- `profiles` merged into `users` — no independent lifecycle.
- `sports_categories` implemented as an enum-ish lookup column on `sports`; promotes to its own table if categories gain attributes.
- `leagues` ≡ `competitions`: one concept (a followable tournament, e.g. "Formula 1", "Premier League"). API keeps `/api/v1/competitions` as canonical; `/api/v1/leagues` exists as a documented alias so both naming conventions work.
- `circuits` folded into `venues` (a circuit *is* a venue with motorsport geometry in metadata).

### D4 — Cache

**Redis 7**: API response caching with status-aware TTLs (§46: sports/league metadata long → upcoming medium → live seconds → finished long), BullMQ job store, rate limiting later. Cache keys versioned (`v1:` prefix) so schema bumps invalidate cleanly. Redis is a cache, never a source of truth; cold start falls through to Postgres.

### D5 — Job system

**BullMQ** queues on Redis: `sync.schedule`, `sync.live`, `sync.standings`, `sync.results`, plus a 60s scheduler tick that computes per-event refresh cadence (§14): >7d low / <24h medium / <1h high / LIVE very-high / FINISHED backoff. All sync writes flow: validate (Zod) → normalize → upsert by provider mapping → invalidate affected Redis keys → enqueue notifications. Mobile never syncs (§13).

### D6 — Authentication

Application-owned auth now: JWT access (15m) + refresh (30d, rotating, hashed at rest), Argon2id where passwords ever appear (they don't today). Devices registered with push tokens (§26), no limits in dev mode. Google Sign-In and phone OTP land in Milestone 18 behind the same token contract; Firebase vs self-hosted decided then against OTP cost data (§23 explicitly leaves this open). Dev-mode escape hatch: `POST /api/v1/auth/dev/login` issues real tokens only when `DEVELOPMENT_MODE=true` — flagged off elsewhere.

### D7 — Sports API strategy

Provider abstraction `SportsProvider` interface (schedule/results/standings/participants/live-capabilities) with per-sport implementations; providers are pluggable and mapped through `provider_mappings` so internal IDs never leak (§11). Selection matrix maintained in `SPORTS_PROVIDERS.md`.

- **F1 (Phase 1): Jolpica-F1** (`https://api.jolpi.ca/ergast/f1/`) — open, keyless, Ergast-compatible successor; verified serving the live 2026 season during this bootstrap. Rate limit ~4 req/s burst honored client-side with token-bucket pacing.
- **Mock provider** ships fixture data covering UPCOMING/LIVE/FINISHED/POSTPONED/CANCELLED/DELAYED so UI/tests don't wait for real calendars (§62). Mock responses are always tagged `"mock": true` end-to-end — never presented as real (§79).
- Cricket (Sportmonks candidate), football, tennis: evaluated at their phase entry; nothing provider-specific may leak below the adapter layer.

### D8 — Cloud strategy

Local/dev: Docker Compose (`postgres`, `redis`; api runs on host for fast iteration). Production shape documented (AWS ECS+Fargate, RDS, ElastiCache, S3/CloudFront, Sentry) but deliberately unbuilt (§38, §70). One env-var surface (`ENVIRONMENT.md`) shared by both.

### D9 — Widget strategy

Android-first (primary device). Widgets rendered natively via **react-native-android-widget** (JS-defined RemoteViews + included Expo config plugin), families Small/Medium/Large as distinct designs (§27). Data from dedicated lightweight endpoint `GET /api/v1/widgets/:instanceToken/data` (opaque per-instance token, minimal payload, short-TTL cached server-side; widget itself performs no heavy work — §31).

**Platform limitation, stated up front (§79):** Android RemoteViews cannot host true gesture-driven horizontal swipes inside a widget. Page-swipe UX is delivered as tap-to-cycle pages (tap right/left half advances/back) with page dots — the standard RemoteViews pattern. iOS Lock Screen/Live Activities deferred until macOS build infrastructure exists; backend payloads stay platform-neutral.

Live widgets display provider-backed freshness (`lastUpdated`, status) only — Jolpica has no live timing, so live F1 states come from mock fixtures in dev and a licensed provider before any production claim (§32).

### D10 — Testing strategy

- **Unit (Vitest/Jest)**: normalization (provider→domain), timezone math, event-status transitions, entitlement resolution, widget payload shaping. Required green before merge.
- **Integration**: NestJS e2e against the compose stack (real Postgres/Redis), provider adapters hit recorded fixtures (never live in CI).
- **E2E (later)**: Maestro flows (login→home→sport→event→widget add) once UI stabilizes; Detox rejected — heavier than needed for this team size.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| MongoDB primary | Relational domain (§7) |
| Direct mobile→provider calls | Key leakage, no cache control, vendor lock-in (§5) |
| Microservices day one | §70 modular monolith mandate |
| Scraping F1 sites | Licensed/keyless API exists (Jolpica); ToS risk (§6) |
| True in-widget swipe gestures | Impossible over RemoteViews; tap-cycle chosen (D9) |
